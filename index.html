JDK, JRE, JVM là gì?JDK・JRE・JVM とは

JVM (Java Virtual Machine) là một máy ảo thực thi bytecode Java — chính nó là lý do Java "viết một lần, chạy mọi nơi" (write once, run anywhere), vì bytecode không phụ thuộc hệ điều hành, chỉ JVM mới cần biên dịch riêng cho từng nền tảng. JRE (Java Runtime Environment) gồm JVM cộng với các thư viện chuẩn (java.lang, java.util...) cần thiết để chạy chương trình Java, nhưng không có công cụ để biên dịch code. JDK (Java Development Kit) là bộ đầy đủ nhất: bao gồm JRE, trình biên dịch javac, và các công cụ dòng lệnh khác (javadoc, jar, jdb...). Muốn viết code Java thì phải cài JDK, không chỉ JRE.

JVM（Java Virtual Machine）は Java のバイトコードを実行する仮想マシンです。OS に依存しないバイトコードを JVM が各プラットフォーム向けに解釈・実行するため、「一度書けばどこでも動く」が実現します。 JRE（Java Runtime Environment）は JVM に加え、プログラム実行に必要な標準ライブラリ（java.lang、java.util など）を含みますが、コンパイラは含みません。 JDK（Java Development Kit）は JRE に加えてコンパイラ javac やその他のコマンドラインツール（javadoc、jar、jdb など）を含む、開発に必要な完全なセットです。開発には JRE ではなく JDK が必要です。

Lưu ý: Từ Java 11 trở đi, Oracle không phân phối JRE độc lập nữa — chỉ còn JDK.
補足：Java 11 以降、Oracle は単体の JRE を配布しておらず、JDK のみが提供されています。
JSLiên hệ: Khi bạn code JS/Node, bạn chỉ cần cài Node.js (giống JRE — môi trường chạy) rồi gõ node app.js là chạy luôn, vì JS là ngôn ngữ thông dịch (interpreted) — engine đọc và chạy code trực tiếp. Java thì khác: bạn phải biên dịch trước bằng javac ra file .class (bytecode), rồi JVM mới chạy được file đó bằng java. Vậy quy trình Java luôn có 2 bước: viết code → biên dịch → chạy, còn JS chỉ có 1 bước: viết code → chạy.
JS比較：JS/Node で開発する場合、Node.js（JRE に相当する実行環境）をインストールして node app.js を実行するだけです。JS はインタプリタ言語で、エンジンがコードを直接読んで実行するためです。Java は異なり、まず javac で コンパイルして .class（バイトコード）ファイルを生成し、その後 java コマンドで JVM が実行します。つまり Java は常に書く → コンパイル → 実行の2段階、JS は書く → 実行の1段階です。

Cấu trúc một chương trình Javaプログラムの基本構造

Mọi chương trình Java bắt đầu từ một class chứa phương thức main — điểm vào (entry point) mà JVM gọi đầu tiên. Tên file .java phải trùng với tên class public trong đó.

すべての Java プログラムは main メソッドを持つクラスから始まります。これは JVM が最初に呼び出すエントリーポイントです。.java ファイル名は、その中の public クラス名と一致させる必要があります。

JSKhác biệt tư duy quan trọng nhất: Trong JS, bạn có thể viết thẳng console.log("hi") ở ngoài cùng file, không cần bọc trong gì cả. Trong Java, tuyệt đối không có "code rời" nằm ngoài class — mọi biến, mọi hàm (Java gọi là method) đều phải nằm bên trong một class. Đây là điều đầu tiên cần chấp nhận khi chuyển từ JS sang Java: bạn luôn bắt đầu bằng việc nghĩ "cái này thuộc về class nào?" trước khi viết bất kỳ dòng code nào.
JS最も重要な考え方の違い：JS ではファイルの最上位に直接 console.log("hi") と書け、何かで包む必要はありません。Java ではクラスの外に「裸の」コードを置くことは一切できません — すべての変数、すべての関数（Java では「メソッド」と呼びます）は必ずクラスの内側に置く必要があります。これは JS から Java に移るときに最初に受け入れるべき点です：コードを書く前に、常に「これはどのクラスに属するか？」を考えることから始まります。
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}

public static void main(String[] args): static để JVM gọi được mà không cần khởi tạo object; String[] args nhận tham số dòng lệnh.

public static void main(String[] args)：static によりインスタンス化なしで JVM が直接呼び出せます。String[] args はコマンドライン引数を受け取ります。

static nghĩa là gì?static とは何か

Một field/method khai báo static thuộc về bản thân class, không thuộc về từng object riêng lẻ — gọi được trực tiếp qua tên class (ClassName.method()) mà không cần new ra object trước. Ngược lại, field/method không có static (gọi là instance member) chỉ tồn tại sau khi đã tạo object bằng new, và mỗi object có bản sao dữ liệu riêng.

static と宣言されたフィールド/メソッドはクラス自体に属し、個々のオブジェクトには属しません — new でオブジェクトを作らなくても、クラス名から直接呼び出せます（ClassName.method()）。逆に static のないフィールド/メソッド（インスタンスメンバー）は new でオブジェクトを作った後にのみ存在し、オブジェクトごとに別々のデータを持ちます。

class Counter {
    static int totalCount = 0;   // dùng chung cho MỌI object / すべてのオブジェクトで共有
    int idNumber;                 // riêng của từng object / オブジェクトごとに別々

    Counter() {
        totalCount++;
        idNumber = totalCount;
    }
}

Counter.totalCount;  // gọi thẳng qua tên class, không cần new
JSLiên hệ: JS class cũng có static giống hệt về ý tưởng: class Counter { static totalCount = 0; } rồi gọi Counter.totalCount — đây là 1 trong số ít chỗ Java và JS gần như giống nhau 100%, không có gì mới phải học lại.
JS比較：JS の class にも同じ発想の static があります：class Counter { static totalCount = 0; } と書き、Counter.totalCount で呼び出します — これは Java と JS がほぼ100%同じ数少ない箇所の一つで、新しく学び直す必要はありません。

Biến & kiểu dữ liệu変数とデータ型

Java là ngôn ngữ kiểu tĩnh (statically typed) — mỗi biến phải khai báo kiểu rõ ràng. Có hai nhóm kiểu dữ liệu:

Java は静的型付け言語であり、変数には必ず型を明示します。データ型は大きく2種類に分かれます：

Bên cạnh 8 kiểu nguyên thủy trên là kiểu tham chiếu (reference type): String, mảng, class, interface... Biến kiểu tham chiếu lưu địa chỉ tới object trên heap, khác với primitive lưu trực tiếp giá trị trên stack.

上記8つのプリミティブ型に加え、参照型（String、配列、クラス、インターフェースなど）があります。参照型はヒープ上のオブジェクトへの参照を保持するのに対し、プリミティブ型はスタック上に値そのものを保持します。

int age = 25;
double price = 19.99;
boolean isActive = true;
String name = "Kris";       // reference type
var count = 10;             // type inference (Java 10+), vẫn là kiểu tĩnh
JSLiên hệ: Trong JS, bạn khai báo let age = 25; và không cần quan tâm "25 là kiểu gì" — biến còn có thể gán lại kiểu khác bất cứ lúc nào (age = "hai lăm" vẫn chạy được, đây gọi là dynamic typing). Java thì ép kiểu ngay từ lúc khai báo và không cho đổi kiểu sau đó — nếu đã khai báo int age thì age = "hai lăm" sẽ báo lỗi biên dịch ngay lập tức. Đây chính là static typing — nghe lạ nhưng thực ra giúp bạn bắt lỗi sớm hơn nhiều so với JS (giống như bạn dùng TypeScript vậy, nếu bạn từng thử qua).
JS比較：JS では let age = 25; と書けば型を意識する必要はなく、後で age = "twenty five" のように別の型を再代入することも可能です（動的型付け）。Java は宣言時に型を固定し、後から型を変えることはできません — int age と宣言した後に age = "twenty five" とすると即コンパイルエラーになります。これが静的型付けで、一見不便に思えますが、JS より早い段階でバグに気づけるという利点があります（TypeScript を触ったことがあれば近い感覚です）。

Wrapper class & Autoboxingラッパークラスとオートボクシング

8 kiểu nguyên thủy (int, double, boolean...) không phải là object — chúng chỉ là giá trị thô, không có method, không dùng được ở những chỗ Java yêu cầu object (ví dụ Generics ở mục 6, hay Collections ở mục 5). Vì vậy Java cung cấp wrapper class tương ứng cho mỗi kiểu nguyên thủy: int → Integer, double → Double, boolean → Boolean... Đây là lý do bạn luôn thấy viết List<Integer> chứ never List<int> — generics chỉ chấp nhận kiểu tham chiếu (object), không chấp nhận kiểu nguyên thủy.

8つのプリミティブ型（int, double, boolean など）はオブジェクトではありません — 単なる生の値であり、メソッドを持たず、Java がオブジェクトを要求する場面（6章のジェネリクスや5章のコレクションなど）では使えません。そのため Java は各プリミティブ型に対応するラッパークラスを用意しています：int → Integer、double → Double、boolean → Boolean など。これが List<int> ではなく常に List<Integer> と書く理由です — ジェネリクスは参照型（オブジェクト）しか受け付けません。

Từ Java 5, trình biên dịch tự động chuyển đổi qua lại giữa int và Integer khi cần — gọi là autoboxing (int → Integer) và unboxing (Integer → int), giúp bạn không phải tự viết Integer.valueOf(x) thủ công mọi lúc.

Java 5 以降、コンパイラが必要に応じて int と Integer を自動的に相互変換します — オートボクシング（int → Integer）とアンボクシング（Integer → int）と呼ばれ、毎回 Integer.valueOf(x) を手書きする必要がなくなります。

List<Integer> scores = new ArrayList<>();
scores.add(90);              // autoboxing: int 90 -> Integer tự động
int first = scores.get(0);   // unboxing: Integer -> int tự động
Cẩn thận: Integer là object nên có thể là null — nếu unboxing 1 biến Integer đang null thành int, chương trình sẽ ném NullPointerException. Đây là lỗi runtime rất phổ biến với người mới.
注意：Integer はオブジェクトなので null になり得ます — null の Integer を int にアンボクシングすると NullPointerException が発生します。初心者が非常によく遭遇する実行時エラーです。

Toán tử演算子

Java hỗ trợ đầy đủ các nhóm toán tử: số học (+ - * / %), so sánh (== != > <), logic (&& || !), gán (= += -=), bitwise (& | ^ ~ << >>) và toán tử ba ngôi ? :.

Java には算術演算子（+ - * / %）、比較演算子（== != > <）、論理演算子（&& || !）、代入演算子（= += -=）、ビット演算子（& | ^ ~ << >>）、三項演算子 ? : があります。

Chú ý: == so sánh reference type sẽ so sánh địa chỉ object, không so sánh giá trị. Dùng .equals() để so sánh nội dung (ví dụ với String).
注意：参照型に対する == はオブジェクトの参照（アドレス）を比較します。内容（値）を比較したい場合（String など）は .equals() を使います。
JSLiên hệ: Nhớ lại JS có == (so sánh lỏng, tự ép kiểu) và === (so sánh chặt, không ép kiểu) — bạn được dạy luôn dùng ===. Java chỉ có duy nhất ==, không có khái niệm "ép kiểu khi so sánh" như JS, nhưng lại có vấn đề khác: == với 2 object (kể cả 2 String giống hệt nội dung) sẽ so sánh xem chúng có phải "cùng 1 ô nhớ" hay không, giống như so sánh 2 object trong JS bằng obj1 === obj2 (vẫn `false` dù nội dung giống nhau nếu là 2 object khác nhau). Muốn so sánh nội dung 2 String trong Java, luôn dùng .equals(), tương tự việc bạn phải tự viết hàm so sánh sâu (deep compare) cho object trong JS.
JS比較：JS には ==（暗黙の型変換あり）と ===（型変換なしの厳密比較）があり、基本 === を使うよう教わったはずです。Java には == しかなく「比較時に型変換する」概念はありませんが、別の落とし穴があります：オブジェクト（内容が同じ String 同士でも）を == で比較すると、「同じメモリ上の実体か」を比較します。これは JS で obj1 === obj2 がオブジェクトの参照比較になり、内容が同じでも別オブジェクトなら false になるのと同じ考え方です。Java で String の内容を比較したいときは必ず .equals() を使います。JS でオブジェクトの深い比較を自作する必要があるのと似ています。

Enum (kiểu liệt kê)Enum（列挙型）

Ở ví dụ switch phía trên, MON, TUE... không phải là chuỗi hay số có sẵn — chúng là các giá trị của một enum, một kiểu dữ liệu đặc biệt dùng để giới hạn biến chỉ được nhận 1 trong số các giá trị cố định đã liệt kê trước, giúp tránh lỗi gõ nhầm chuỗi (vd: gõ nhầm "Mnday") mà compiler không phát hiện được.

上のスイッチの例で MON、TUE は既存の文字列や数値ではなく、enum（列挙型）の値です。enum は変数の値を事前に列挙された固定の候補だけに制限する特別な型で、"Mnday" のようなタイプミスをコンパイラが検出できない、といった文字列特有のミスを防げます。

enum Day {
    MON, TUE, WED, THU, FRI, SAT, SUN
}

Day day = Day.MON;
System.out.println(day); // MON
JSLiên hệ: JS thuần không có enum thật sự — người ta thường giả lập bằng object đóng băng: const Day = Object.freeze({ MON: "MON", TUE: "TUE" }), nhưng JS không hề chặn bạn gán 1 chuỗi bất kỳ khác vào biến đó. TypeScript có enum gần giống Java hơn. Điểm khác biệt: enum Java không chỉ là danh sách hằng số — nó còn có thể có field, method, constructor riêng như 1 class thực thụ, mạnh hơn enum ở hầu hết ngôn ngữ khác.
JS比較：素の JS には本当の意味での enum はなく、通常は凍結したオブジェクトで代用します：const Day = Object.freeze({ MON: "MON", TUE: "TUE" })。しかし JS はそれ以外の任意の文字列を代入することを止めてくれません。TypeScript の enum は Java により近いです。違いとして、Java の enum は単なる定数リストではなく、フィールド・メソッド・コンストラクタを持てる本物のクラスのような存在で、他の多くの言語の enum よりも強力です。

Mảng (Array) & String配列と String

Mảng trong Java có kích thước cố định khi khởi tạo, lưu trên heap và là reference type dù chứa primitive. String là immutable (bất biến) — mọi thao tác như concat, substring đều tạo ra object String mới thay vì sửa object cũ. Vì lý do hiệu năng khi nối chuỗi nhiều lần, nên dùng StringBuilder.

配列はサイズが初期化時に固定され、ヒープに格納される参照型です（要素がプリミティブでも）。String は不変（immutable）で、concat や substring などの操作は元のオブジェクトを変更せず、新しい String オブジェクトを生成します。文字列結合を繰り返す場合はパフォーマンスのため StringBuilder を使用します。

int[] numbers = {1, 2, 3, 4, 5};
String[] names = new String[3];

StringBuilder sb = new StringBuilder();
for (String n : names) {
    sb.append(n).append(", ");
}
JSLiên hệ: Mảng JS (const arr = [1,2,3]) có thể push/pop tự do, thay đổi độ dài linh hoạt. Mảng Java thì cố định độ dài ngay khi tạo — khai báo int[] numbers = new int[5] là chỉ có đúng 5 ô, không thêm/bớt được. Nếu bạn cần một "mảng" co giãn được như JS array, trong Java bạn dùng ArrayList (xem mục Collections bên dưới) chứ không dùng array thường. Về String thì giống JS: cả 2 ngôn ngữ đều coi string là immutable — str + "abc" trong JS cũng tạo ra string mới chứ không sửa string cũ, y hệt Java.
JS比較：JS の配列（const arr = [1,2,3]）は push/pop で自由に長さを変えられます。Java の配列は生成時に長さが固定されます — int[] numbers = new int[5] と書けば要素は5個だけで増減できません。JS 配列のように伸び縮みするデータ構造が欲しい場合は、通常の配列ではなく ArrayList（後述の Collections 参照）を使います。String については JS と同じ考え方です：どちらの言語も string は不変（immutable）で、JS の str + "abc" も元の文字列を変更せず新しい文字列を作る点は Java と全く同じです。

Class, Object & Constructorクラス・オブジェクト・コンストラクタ

Class là khuôn mẫu định nghĩa thuộc tính (field) và hành vi (method); Object là thực thể được tạo ra từ class bằng từ khóa new. Constructor là phương thức đặc biệt trùng tên class, chạy khi object được khởi tạo, dùng để thiết lập giá trị ban đầu.

クラスはフィールド（属性）とメソッド（振る舞い）を定義する設計図であり、オブジェクトは new キーワードによってクラスから生成される実体です。コンストラクタはクラス名と同じ名前を持つ特殊なメソッドで、オブジェクト生成時に呼ばれ初期値を設定します。

public class Employee {
    private String name;
    private double salary;

    public Employee(String name, double salary) {
        this.name = name;
        this.salary = salary;
    }

    public double getSalary() { return salary; }
}

Employee e = new Employee("Kris", 2000.0);
JSLiên hệ: Tin vui là cú pháp class trong JS (ES6+) trông gần giống hệt Java: constructor(name, salary) { this.name = name; }. Khác biệt lớn nhất nằm ở "phía dưới": JS class thực chất chỉ là lớp vỏ cú pháp (syntactic sugar) phủ lên prototype — object JS vẫn linh hoạt, bạn có thể thêm/xóa property bất cứ lúc nào (e.age = 30 dù class không khai báo age). Java class là khuôn cứng: field phải khai báo trước, không thể tự thêm field mới cho object lúc runtime.
JS比較：朗報として、JS（ES6+）の class 構文は Java とほぼ同じ見た目です：constructor(name, salary) { this.name = name; }。最大の違いは「裏側」にあります：JS の class はプロトタイプの上に被せた糖衣構文にすぎず、オブジェクトは依然として柔軟で、いつでもプロパティを追加・削除できます（class に age がなくても e.age = 30 は通ります）。Java のクラスは厳格な型で、フィールドは事前宣言が必須であり、実行時にオブジェクトへ新しいフィールドを勝手に追加することはできません。

4 tính chất của OOPOOP の4つの原則

Encapsulation (Tính đóng gói): ẩn dữ liệu nội bộ bằng access modifier (private), chỉ cho truy cập qua getter/setter — bảo vệ tính toàn vẹn dữ liệu.

カプセル化：アクセス修飾子（private）で内部データを隠蔽し、getter/setter 経由でのみアクセスさせることでデータの整合性を守ります。

Inheritance (Tính kế thừa): class con (extends) tái sử dụng field/method từ class cha, giúp tránh lặp code.

継承：サブクラスが extends によって親クラスのフィールド・メソッドを再利用でき、コードの重複を防ぎます。

Khi class con có constructor riêng, dòng đầu tiên bên trong constructor đó cần gọi super(...) để chạy constructor của class cha trước — đảm bảo phần dữ liệu kế thừa từ cha được khởi tạo đầy đủ trước khi class con khởi tạo phần của riêng nó. Nếu bạn không tự viết super(...), Java tự động chèn super() không tham số vào đầu constructor giúp bạn.

サブクラスが独自のコンストラクタを持つ場合、そのコンストラクタの最初の行で super(...) を呼び出し、先に親クラスのコンストラクタを実行する必要があります — サブクラス独自の部分を初期化する前に、親から継承した部分が確実に初期化されるようにするためです。自分で super(...) を書かなければ、Java が引数なしの super() を自動的にコンストラクタの先頭に挿入します。

class Animal {
    String name;
    Animal(String name) { this.name = name; }
}

class Dog extends Animal {
    String breed;
    Dog(String name, String breed) {
        super(name);     // BẮT BUỘC gọi trước, chạy constructor của Animal
        this.breed = breed;
    }
}

Polymorphism (Tính đa hình): một phương thức có thể hoạt động khác nhau tùy vào object gọi nó — gồm overriding (ghi đè method ở class con, xác định lúc runtime) và overloading (nhiều method cùng tên khác tham số, xác định lúc compile).

多態性（ポリモーフィズム）：呼び出すオブジェクトによって同じメソッドが異なる振る舞いをします。サブクラスでのメソッドのオーバーライド（実行時に決定）と、同名で引数が異なるオーバーロード（コンパイル時に決定）があります。

Abstraction (Tính trừu tượng): chỉ để lộ hành vi cần thiết, ẩn chi tiết cài đặt — thực hiện qua abstract class hoặc interface.

抽象化：必要な振る舞いのみを公開し、実装の詳細を隠します。abstract class や interface によって実現されます。

abstract class Animal {
    abstract void makeSound(); // chưa cài đặt / 実装なし
}

class Dog extends Animal {
    @Override
    void makeSound() { System.out.println("Woof"); } // overriding
}
JSLiên hệ: JS cho phép đặt giá trị mặc định ngay trên tham số hàm: function greet(name = "Guest") {}. Java không có cú pháp default parameter — muốn có hiệu ứng tương tự, bạn dùng overloading: viết nhiều method cùng tên với số tham số khác nhau, method ít tham số hơn sẽ gọi tới method đủ tham số kèm giá trị mặc định.
JS比較：JS では引数にデフォルト値を直接書けます：function greet(name = "Guest") {}。Java にはデフォルト引数の構文がありません — 同様の効果を得るにはオーバーロードを使います：同じ名前で引数の数が異なる複数のメソッドを書き、引数が少ない方から、デフォルト値付きで引数が多い方を呼び出します。
void greet(String name) {
    greet(name, "Guest"); // gọi overload còn lại với giá trị mặc định
}
void greet(String name, String defaultTitle) {
    System.out.println(name + " (" + defaultTitle + ")");
}

Nếu 2 class cha cùng có 1 method giống hệt tên (khác cách cài đặt), class con kế thừa cả 2 sẽ không biết dùng bản nào — đây gọi là "diamond problem". なぜクラスは1つしか extends できないのに、interface は複数 implements できるのか？ 2つの親クラスが同名だが実装が異なるメソッドを持っていた場合、両方を継承した子クラスはどちらを使うべきか分かりません — これが「ダイヤモンド問題」です。Java はクラスを単一継承のみに制限することでこれを回避しています。interface が安全な理由は（Java 8以前は）実装部分を持たず「どんなメソッドが必要か」だけを宣言するため、衝突のしようがなく、いくつ implement しても問題にならないからです。

Xử lý ngoại lệ (Exception Handling)

例外処理

try-catch-finally & phân loại Exceptiontry-catch-finally と例外の分類

Java phân loại lỗi thành Checked Exception (bắt buộc xử lý hoặc khai báo throws, vd: IOException) và Unchecked Exception (kế thừa RuntimeException, không bắt buộc xử lý, vd: NullPointerException, thường do lỗi logic). Error (vd: OutOfMemoryError) là lỗi nghiêm trọng ở tầng JVM, không nên tự xử lý.

Java の例外はチェック例外（処理必須か throws 宣言が必要、例：IOException）と非チェック例外（RuntimeException を継承、処理任意、例：NullPointerException、多くはロジックエラー）に分類されます。Error（例：OutOfMemoryError）は JVM レベルの重大なエラーで、通常は自前で処理すべきではありません。

try {
    int result = 10 / divisor;
} catch (ArithmeticException e) {
    System.out.println("Lỗi chia cho 0: " + e.getMessage());
} finally {
    System.out.println("Luôn chạy dù có lỗi hay không");
}

// try-with-resources: tự động đóng resource (Java 7+)
try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
    br.readLine();
}
JSLiên hệ: Cấu trúc try { } catch (e) { } finally { } gần như giống hệt JS, nên phần này bạn học rất nhanh. Điểm khác biệt lớn nhất là Checked Exception — khái niệm JS hoàn toàn không có. Trong JS, hàm nào cũng có thể throw bất cứ lúc nào mà không cần khai báo trước. Trong Java, nếu một method có khả năng ném IOException (checked), compiler bắt buộc bạn phải catch nó hoặc khai báo throws IOException ở chữ ký method — nếu không code sẽ không biên dịch được. Đây là điểm dễ gây khó chịu nhất cho người quen JS lúc mới học Java.
JS比較：try { } catch (e) { } finally { } の構文は JS とほぼ同じなので、ここはすぐに理解できるはずです。最大の違いはチェック例外で、JS には全く存在しない概念です。JS ではどの関数もいつでも自由に throw でき、事前宣言は不要です。Java では、あるメソッドが IOException（チェック例外）を投げる可能性がある場合、コンパイラが catch するかメソッドシグネチャに throws IOException と宣言することを強制します — さもないとコンパイルが通りません。これは JS に慣れた人が Java を学び始めたときに最も戸惑いやすいポイントです。

独自の例外は Exception（チェック例外）または RuntimeException（非チェック例外）を継承して作成し、ビジネス上の意味をより明確に伝えられます。

public class InsufficientBalanceException extends RuntimeException {
    public InsufficientBalanceException(String message) {

Collections Framework

コレクションフレームワーク

List, Set, Map, QueueList・Set・Map・Queue

Collections Framework cung cấp cấu trúc dữ liệu chuẩn hóa để lưu và thao tác nhóm object:

コレクションフレームワークは、オブジェクトの集合を格納・操作するための標準化されたデータ構造を提供します：

  • List (ArrayList, LinkedList): có thứ tự, cho phép trùng lặp. ArrayList truy cập nhanh (O(1)) nhưng chèn/xóa giữa mảng chậm; LinkedList ngược lại.
  • Set (HashSet, TreeSet, LinkedHashSet): không cho trùng lặp. HashSet không đảm bảo thứ tự; TreeSet tự sắp xếp; LinkedHashSet giữ thứ tự chèn.
  • Map (HashMap, TreeMap, LinkedHashMap): lưu cặp key-value, key không trùng lặp.
  • Queue / Deque (ArrayDeque, PriorityQueue): xử lý theo hàng đợi FIFO hoặc có độ ưu tiên.
  • List（ArrayList, LinkedList）：順序があり重複を許可。ArrayList はランダムアクセスが速い（O(1)）が中間の挿入・削除は遅い。LinkedList はその逆。
  • Set（HashSet, TreeSet, LinkedHashSet）：重複を許可しない。HashSet は順序保証なし、TreeSet は自動ソート、LinkedHashSet は挿入順を維持。
  • Map（HashMap, TreeMap, LinkedHashMap）：キーと値のペアを保持し、キーは重複不可。
  • Queue / Deque（ArrayDeque, PriorityQueue）：FIFO または優先度付きキューとして処理。

Map<String, Integer> scores = new HashMap<>();
scores.put("Kris", 95);

    System.out.println(entry.getKey() + ": " + entry.getValue());
}

Khác biệt: JS Map/Set không cần khai báo kiểu dữ liệu bên trong, còn Java bắt bạn khai báo rõ Map<String, Integer> (kiểu key, kiểu value). Còn List trong Java thì đóng vai trò giống hệt Array trong JS — chỉ khác là ArrayList cần khai báo kiểu phần tử bên trong (List<String>), không thể trộn lẫn nhiều kiểu dữ liệu trong cùng 1 list như JS array ([1, "a", true] hợp lệ trong JS nhưng không hợp lệ trong Java List thường).
JS比較：ここは最も馴染みやすい部分でしょう。モダン JS（ES6+）にはすでに Map と Set があり、考え方は Java とほぼ同じです：new Map() はキーと値を保持する点で HashMap と同じ、new Set() は重複を排除する点で HashSet と同じです。違いは、JS の Map/Set は内部の型を宣言する必要がないのに対し、Java は Map<String, Integer>（キーの型・値の型）を明示する必要がある点です。Java の List は JS の Array と同じ役割を果たしますが、要素の型（List<String>）を宣言する必要があり、JS の配列（[1, "a", true] のように複数の型を混在できる）とは異なり、1つの List には1種類の型しか入れられません。

Iterator cho phép duyệt collection an toàn và hỗ trợ xóa phần tử trong lúc duyệt (khác với vòng for-each sẽ ném ConcurrentModificationException nếu sửa collection). Comparable (method compareTo) định nghĩa thứ tự tự nhiên ngay trong class; Comparator định nghĩa thứ tự tùy biến bên ngoài, linh hoạt hơn khi cần nhiều cách sắp xếp.

Iterator はコレクションを安全に走査でき、走査中の要素削除にも対応します（for-each でコレクションを変更すると ConcurrentModificationException が発生します）。Comparable（compareTo メソッド）はクラス自身に自然順序を定義し、Comparator は外部でカスタムの順序を定義でき、複数のソート基準が必要な場合に柔軟です。

Generics

ジェネリクス

Generics cho phép class, interface, method thao tác trên kiểu dữ liệu được tham số hóa, giúp kiểm tra kiểu tại compile-time thay vì runtime, tránh ClassCastException và loại bỏ nhu cầu ép kiểu thủ công.

ジェネリクスにより、クラス・インターフェース・メソッドを型パラメータで抽象化でき、コンパイル時に型チェックが行われるため ClassCastException を防ぎ、手動キャストが不要になります。

class Box<T> {
    private T content;
    public void set(T content) { this.content = content; }
    public T get() { return content; }
}

Box<String> box = new Box<>();
box.set("Hello");

// Bounded type parameter
public static <T extends Comparable<T>> T max(List<T> list) { ... }

// Wildcard
public void printAll(List<? extends Number> list) { ... }
JSLiên hệ: JS thuần không có generics vì JS không kiểm tra kiểu lúc biên dịch. Nếu bạn từng thấy cú pháp Array<string> hoặc Box<T> trong TypeScript, đó chính xác là generics — TypeScript "mượn" ý tưởng này gần như nguyên vẹn từ Java/C#. Nếu bạn chưa dùng TS, cứ hiểu đơn giản: Generics giống như bạn viết 1 hàm xử lý "hộp đựng đồ" (Box) dùng chung được cho mọi loại đồ vật (String, Integer, Employee...) mà không cần viết lại class riêng cho từng loại.
JS比較：素の JS はコンパイル時の型チェックがないため generics の概念はありません。TypeScript の Array<string> や Box<T> のような構文を見たことがあれば、それがまさにジェネリクスです — TypeScript はこの発想を Java/C# からほぼそのまま取り入れています。TS を使ったことがなければ、シンプルに「あらゆる種類の中身（String、Integer、Employee など）を入れられる汎用の『箱』を、種類ごとにクラスを書き直さずに1つのコードで扱える仕組み」と考えればOKです。

Java dùng cơ chế type erasure: thông tin generic bị xóa sau compile, chỉ tồn tại lúc biên dịch để kiểm tra kiểu — đây là lý do không thể tạo new T() hay mảng generic trực tiếp.

Java は型消去（type erasure）を採用しており、ジェネリック情報はコンパイル後に消去され、コンパイル時の型チェックにのみ使われます。そのため new T() やジェネリック配列を直接作成することはできません。

Kiến trúc JVM

JVM アーキテクチャ

JVM Memory ModelJVM メモリモデル

  • Heap: vùng nhớ chứa toàn bộ object, được chia sẻ giữa các thread, chịu sự quản lý của Garbage Collector. Chia thành Young Generation (Eden, Survivor) và Old Generation.
  • Stack: mỗi thread có một stack riêng, lưu thông tin frame của method (biến local, giá trị tham số). Kích thước cố định, gây StackOverflowError nếu đệ quy quá sâu.
  • Method Area / Metaspace: lưu metadata class, constant pool, thông tin static. Từ Java 8, PermGen được thay bằng Metaspace (dùng native memory thay vì heap).
  • PC Register & Native Method Stack: hỗ trợ thực thi lệnh và gọi hàm native (JNI).
JSLiên hệ: Node.js chạy trên engine V8 — về vai trò, V8 tương đương JVM (đều là "cỗ máy" chạy code đã biên dịch/tối ưu). Nhưng có 1 khác biệt cực kỳ quan trọng bạn cần nhớ xuyên suốt phần còn lại của tài liệu: JS/Node vận hành theo mô hình single-threaded + event loop (1 luồng chính duy nhất, việc bất đồng bộ như fetch/setTimeout được đẩy vào hàng đợi rồi xử lý sau). JVM thì ngược lại: hỗ trợ đa luồng thật sự (true multithreading) — nhiều thread có thể chạy song song trên nhiều nhân CPU cùng lúc, đây là lý do phần "Đa luồng & Concurrency" ở mục 8 rất quan trọng và không có khái niệm tương đương 1-1 trong JS thuần.
JS比較：Node.js は V8 エンジン上で動作し、役割としては V8 が JVM に相当します（どちらもコンパイル・最適化されたコードを実行する「エンジン」）。ただし、この先の内容を理解する上で非常に重要な違いがあります：JS/Node はシングルスレッド + イベントループモデルで動作します（メインスレッドは1つだけで、fetch や setTimeout のような非同期処理はキューに入れられ後で処理されます）。JVM はその逆で、本当の意味でのマルチスレッドをサポートします — 複数のスレッドが複数の CPU コア上で本当に並列実行されます。これが後述の「マルチスレッドと並行処理」（8章）が重要であり、素の JS には1対1で対応する概念がない理由です。
  • ヒープ：すべてのオブジェクトを格納する領域で、スレッド間で共有され、ガベージコレクタが管理します。Young Generation（Eden、Survivor）と Old Generation に分かれます。
  • スタック：スレッドごとに独立し、メソッドのフレーム情報（ローカル変数、引数）を保持します。サイズは固定で、再帰が深すぎると StackOverflowError が発生します。
  • メソッドエリア / Metaspace：クラスのメタデータ、定数プール、static 情報を保持します。Java 8 以降、PermGen は Metaspace（ヒープではなくネイティブメモリを使用）に置き換えられました。
  • PC レジスタ & ネイティブメソッドスタック：命令実行やネイティブ関数呼び出し（JNI）を支援します。

Class Loading & Bytecodeクラスローディングとバイトコード

Khi chương trình chạy, ClassLoader nạp file .class (bytecode) theo 3 bước: Loading (đọc bytecode vào bộ nhớ), Linking (Verify → Prepare → Resolve), Initialization (chạy static initializer). Cơ chế phân cấp gồm Bootstrap → Platform → Application ClassLoader, tuân theo nguyên tắc parent delegation (ủy quyền lên cha trước khi tự tải).

プログラム実行時、ClassLoader が .class ファイル（バイトコード）を3段階でロードします：Loading（バイトコードをメモリに読み込む）、Linking（Verify → Prepare → Resolve）、Initialization（static 初期化子の実行）。階層は Bootstrap → Platform → Application ClassLoader となり、親委譲モデル（まず親に委譲してからロードする）に従います。

Garbage Collectionガベージコレクション

GC tự động thu hồi bộ nhớ của object không còn được tham chiếu, dựa trên thuật toán Mark-and-Sweep (đánh dấu object còn sống, dọn object chết) kết hợp với generational hypothesis (đa số object "chết trẻ"). Các collector phổ biến: Serial, Parallel, G1 (Garbage First — mặc định từ Java 9), và ZGC/Shenandoah cho ứng dụng cần độ trễ cực thấp.

GC は参照されなくなったオブジェクトのメモリを自動的に回収します。Mark-and-Sweep（生存オブジェクトをマークし、死んだオブジェクトを回収）と世代別仮説（多くのオブジェクトは「若くして死ぬ」）に基づきます。代表的なコレクタ：Serial、Parallel、G1（Java 9 以降のデフォルト）、超低遅延が必要なアプリ向けの ZGC/Shenandoah。

Thread & RunnableThread と Runnable

Có 2 cách tạo thread: kế thừa Thread, hoặc implement Runnable rồi truyền vào Thread — cách thứ hai được khuyến khích vì Java không hỗ trợ đa kế thừa, giữ class linh hoạt hơn.

スレッド作成には2通りあります：Thread を継承する方法と、Runnable を実装して Thread に渡す方法。Java は多重継承をサポートしないため、クラスの柔軟性を保てる後者が推奨されます。

Runnable task = () -> System.out.println("Running in: " + Thread.currentThread().getName());
Thread t = new Thread(task);
t.start(); // KHÔNG gọi t.run() trực tiếp — sẽ chạy trên thread hiện tại, không tạo thread mới
JSLiên hệ: Đây là phần khác biệt tư duy lớn nhất so với JS. Trong JS, khi bạn viết code "bất đồng bộ" bằng async/await hay Promise, code đó vẫn chạy trên cùng 1 thread chính — chỉ là được lập lịch chạy sau thông qua event loop, không có 2 đoạn code JS nào thực sự chạy song song cùng lúc (trừ khi bạn dùng Worker Threads, vốn khá ít dùng). Trong Java, new Thread(task).start() tạo ra một luồng thực thi song song thật sự với thread chính — 2 đoạn code có thể chạy đồng thời trên 2 nhân CPU khác nhau. Đây chính là lý do Java cần các cơ chế như synchronized ở mục dưới: để tránh 2 thread cùng sửa 1 biến chung cùng lúc gây lỗi — vấn đề mà lập trình JS thông thường hiếm khi gặp phải.
JS比較：ここは JS との考え方の違いが最も大きい部分です。JS で async/await や Promise を使って「非同期」コードを書いても、そのコードは依然として同じメインスレッド上で実行されます — イベントループによって後で実行されるようスケジュールされるだけで、2つの JS コードが本当に同時に並列実行されることはありません（あまり使われない Worker Threads を使う場合を除く）。Java では new Thread(task).start() によって、メインスレッドとは本当に並列実行されるスレッドが作られます — 2つのコードが異なる CPU コア上で同時に動く可能性があります。これが後述の synchronized のような仕組みが Java に必要な理由です：複数スレッドが同じ変数を同時に変更してしまう問題を防ぐためで、通常の JS プログラミングではほとんど遭遇しない問題です。

Synchronized & LockSynchronized と Lock

Khi nhiều thread truy cập chung một tài nguyên (race condition), cần đồng bộ hóa. Từ khóa synchronized đảm bảo chỉ một thread giữ "khóa" (monitor) của object/method tại một thời điểm. java.util.concurrent.locks.ReentrantLock linh hoạt hơn synchronized: cho phép thử khóa có timeout (tryLock), khóa công bằng (fair lock), và unlock tường minh.

複数スレッドが共有リソースにアクセスする際（競合状態）、同期が必要です。synchronized キーワードは、ある時点で1つのスレッドのみがオブジェクト/メソッドの「ロック」（モニター）を保持することを保証します。java.util.concurrent.locks.ReentrantLock はより柔軟で、タイムアウト付きロック試行（tryLock）、公平ロック、明示的な unlock が可能です。

private final Object lock = new Object();
public void increment() {
    synchronized (lock) {
        counter++;
    }
}

ExecutorServiceExecutorService

Thay vì tự tạo/quản lý Thread thủ công, ExecutorService quản lý một thread pool, tái sử dụng thread để giảm chi phí tạo/hủy, phù hợp cho ứng dụng xử lý nhiều tác vụ ngắn.

スレッドを自前で作成・管理する代わりに、ExecutorService はスレッドプールを管理し、スレッドを再利用することで生成・破棄のコストを削減します。多数の短いタスクを処理するアプリケーションに適しています。

ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(() -> System.out.println("Task executed"));
executor.shutdown();

SingletonSingleton

Đảm bảo một class chỉ có duy nhất một instance trong toàn ứng dụng, thường dùng cho config, connection pool, logger.

アプリケーション全体でクラスのインスタンスが1つだけであることを保証します。設定管理、コネクションプール、ロガーなどに使われます。

public class AppConfig {
    private static volatile AppConfig instance;
    private AppConfig() {}

    public static AppConfig getInstance() {
        if (instance == null) {
            synchronized (AppConfig.class) {
                if (instance == null) instance = new AppConfig();
            }
        }
        return instance;
    }
}
JSLiên hệ: Trong JS, bạn thường "vô tình" đạt được Singleton chỉ bằng cách export 1 object từ module: export default { count: 0 } — vì mỗi module trong JS chỉ được load 1 lần và dùng chung ở mọi nơi import nó, tự nhiên đã là singleton. Java không có sẵn cơ chế module-level object như vậy, nên phải tự viết pattern này bằng tay như code ví dụ trên.
JS比較：JS では、モジュールから1つのオブジェクトを export するだけで「自然に」Singleton になることがよくあります：export default { count: 0 } — JS の各モジュールは1度だけロードされ、import した場所すべてで共有されるため、自動的に singleton になります。Java にはそのようなモジュールレベルの共有オブジェクトの仕組みがないため、上記のように自分でこのパターンを書く必要があります。

JSLiên hệ: Bạn chắc chắn đã dùng Observer pattern rồi mà không để ý — element.addEventListener('click', handler) chính là Observer: element là "subject", các hàm callback đăng ký qua addEventListener là "observer". Stream API (java.util.stream)Stream API

Từ Java 8, Stream API cho phép xử lý collection theo phong cách khai báo (declarative) và có thể chạy song song, thay vì viết vòng lặp thủ công. Stream có 2 loại thao tác: intermediate (map, filter, sorted — trả về Stream mới, lazy) và terminal (collect, forEach, reduce — kích hoạt thực thi và trả kết quả).

Java 8 以降、Stream API により手動のループの代わりに宣言的なスタイルでコレクションを処理でき、並列実行も可能です。ストリームの操作は2種類：中間操作（map, filter, sorted — 新しい Stream を返す、遅延評価）と終端操作（collect, forEach, reduce — 実行をトリガーし結果を返す）。

List<String> result = employees.stream()
    .filter(e -> e.getSalary() > 1000)
    .map(Employee::getName)
    .sorted()
    .collect(Collectors.toList());
JSLiên hệ: Đây có lẽ là phần bạn sẽ thấy "à, giống hệt cái mình đã biết!" — Stream API của Java gần như là bản sao ý tưởng của chuỗi array.filter().map().sort() trong JS. So sánh trực tiếp: .filter(e -> ...) ≈ JS .filter(e => ...); .map(Employee::getName) ≈ JS .map(e => e.getName()); .collect(Collectors.toList()) ≈ JS tự động trả về array mới, không cần bước "collect" riêng. Khác biệt chính: Java Stream chỉ dùng được 1 lần duy nhất (dùng xong phải tạo stream mới), còn JS array method có thể gọi lại nhiều lần trên cùng array gốc.
JS比較：ここは「あ、知ってるやつだ！」となる部分でしょう。Java の Stream API は JS の array.filter().map().sort() のメソッドチェーンとほぼ同じ発想です。直接対応させると：.filter(e -> ...) ≈ JS の .filter(e => ...)；.map(Employee::getName) ≈ JS の .map(e => e.getName())；.collect(Collectors.toList()) ≈ JS では自動的に新しい配列が返るため「collect」という別ステップは不要です。主な違いは、Java の Stream は一度しか使えない点（使用後は新しい stream を作り直す必要がある）で、JS の配列メソッドは同じ元の配列に対して何度でも呼び出せます。

Ví dụ đối chiếu: lọc Task ưu tiên cao対比例：優先度の高い Task の抽出

const highPriorityTitles = tasks

Java

    .filter(t -> t.getPriority() == 1)
    .map(Task::getTitle)
    .collect(Collectors.toList());

Gần như dịch 1-1 từng dòng. Điểm khác duy nhất đáng chú ý: Task::getTitle là method reference — cách viết gọn hơn của t -> t.getTitle(), tương đương JS viết tắt t => t.title thành... vẫn chính nó (JS không có cú pháp rút gọn thêm cho trường hợp này).

ほぼ1行ずつそのまま対応します。唯一注目すべき違いは、Task::getTitle がメソッド参照である点です — t -> t.getTitle() をさらに簡潔に書いた形で、JS の t => t.title をさらに省略する構文に相当しますが、JS にはこのケース向けのこれ以上の省略記法はありません。

Lambda & Functional Interfaceラムダ式と関数型インターフェース

Functional Interface là interface chỉ có đúng 1 abstract method (vd: Runnable, Comparator), cho phép biểu diễn bằng lambda expression ngắn gọn thay vì anonymous class. Java cung cấp sẵn bộ interface phổ biến trong java.util.function: Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>.

関数型インターフェースは抽象メソッドを1つだけ持つインターフェース（例：Runnable, Comparator）で、匿名クラスの代わりに簡潔なラムダ式で表現できます。Java は java.util.function に Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T> などの標準インターフェースを提供します。

Comparator<Employee> byName = (a, b) -> a.getName().compareTo(b.getName());
Function<Integer, Integer> square = x -> x * x;
JSLiên hệ: Lambda x -> x * x trong Java về bản chất chính là arrow function x => x * x trong JS — cùng mục đích: viết hàm ngắn gọn không cần đặt tên. Điểm khác: mỗi lambda Java phải "khớp" với đúng 1 functional interface có sẵn kiểu tham số/kiểu trả về (vd: Function<Integer, Integer>), trong khi JS arrow function không ràng buộc kiểu gì cả, muốn truyền tham số nào cũng được.
JS比較：Java のラムダ x -> x * x は、本質的に JS のアロー関数 x => x * x と同じものです — 名前を付けずに簡潔に関数を書くという目的も同じです。違いは、Java の各ラムダは型が決まった関数型インターフェース（例：Function<Integer, Integer>）と一致している必要がある点で、JS のアロー関数は型の制約がなく、どんな引数でも自由に渡せます。

var, Records, Switch expressionvar・Records・Switch 式

var (Java 10+) cho phép trình biên dịch tự suy luận kiểu, biến vẫn giữ kiểu tĩnh — chỉ giảm việc gõ lặp lại. Record (Java 16+) là cách ngắn gọn để tạo class chứa dữ liệu bất biến (immutable data carrier), tự sinh constructor, getter, equals, hashCode, toString.

var（Java 10+）はコンパイラに型推論させますが、変数は依然として静的型を持ちます — 冗長な記述を減らすだけです。Record（Java 16+）は不変のデータ保持クラスを簡潔に定義する方法で、コンストラクタ、getter、equals、hashCode、toString が自動生成されます。

record Point(int x, int y) {}

var p = new Point(3, 4);
System.out.println(p.x() + ", " + p.y());
JSLiên hệ: record Point(int x, int y) {} gần giống việc bạn viết const point = { x: 3, y: 4 } trong JS rồi Object.freeze(point) để không cho sửa (immutable) — nhưng Java tự sinh thêm getter/equals/toString giúp bạn, còn JS bạn phải tự viết hoặc dùng thư viện. var của Java và let/const của JS trông giống nhau về mặt "không cần gõ kiểu", nhưng nhắc lại: var Java vẫn có kiểu cố định ẩn bên trong, chỉ là compiler tự đoán giúp bạn — khác hẳn bản chất "không có kiểu cố định" của biến JS.
JS比較：record Point(int x, int y) {} は、JS で const point = { x: 3, y: 4 } と書いて Object.freeze(point) で変更不可にする（immutable にする）のに近い発想ですが、Java は getter・equals・toString を自動生成してくれる点が異なり、JS では自分で書くかライブラリに頼る必要があります。Java の var と JS の let/const は「型を書かなくていい」という点で似て見えますが、繰り返しになりますが Java の var は内部的には型が固定されており、コンパイラが推論しているだけです — 型が固定されない JS の変数とは本質的に異なります。

React là gì? Tư duy "khai báo UI"React とは？「宣言的 UI」という考え方

React là một thư viện JavaScript (không phải framework đầy đủ) để xây dựng giao diện người dùng, phát triển bởi Meta. Ý tưởng cốt lõi: bạn mô tả UI trông như thế nào ứng với từng trạng thái dữ liệu (khai báo/declarative), thay vì viết từng bước thao tác DOM thủ công (mệnh lệnh/imperative) như JS thuần.

React は Meta が開発した、UI 構築のための JavaScript ライブラリです（フルスタックのフレームワークではありません）。核心となる考え方は、データの状態ごとに UI がどう見えるべきかを記述する（宣言的）ことであり、素の JS のように DOM 操作を1手順ずつ命令する（命令的）のとは異なります。

Vanilla JS (imperative) 
const btn = document.createElement("button");
btn.textContent = "Đã thích: 0";
let count = 0;
btn.addEventListener("click", () => {
  count++;
  btn.textContent = "Đã thích: " + count;
});
document.body.appendChild(btn);
React (declarative) 
function LikeButton() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      Đã thích: {count}
    </button>
  );
}

Ở bản React, bạn không tự tay cập nhật textContent — bạn chỉ nói "khi count thay đổi, nút này hiển thị con số đó", React tự lo phần cập nhật DOM.

React 版では自分で textContent を更新しません — 「count が変わったら、このボタンはその数値を表示する」と宣言するだけで、DOM の更新は React が引き受けます。

JSX cơ bảnJSX の基本

JSX là phần mở rộng cú pháp cho JS, cho phép viết cấu trúc giống HTML ngay trong file JS. Đây không phải HTML thật — nó được biên dịch (qua Babel/esbuild) thành lời gọi hàm React.createElement(...). Vài quy tắc quan trọng:

JSX は JS の構文拡張で、JS ファイルの中に HTML のような構造を書けるようにします。本物の HTML ではなく、（Babel/esbuild によって）React.createElement(...) の呼び出しにコンパイルされます。いくつかの重要なルールがあります：

  • Phải có đúng 1 thẻ gốc bao ngoài cùng (hoặc dùng <>...</> — Fragment — nếu không muốn thêm thẻ thừa).
  • Thuộc tính viết theo camelCase: onclick → onClick, class → className (vì class là từ khóa JS).
  • Nhúng biểu thức JS bằng dấu ngoặc nhọn đơn { }.
  • Thẻ không có nội dung con phải tự đóng: <img />, <br />.
  • 最も外側にちょうど1つのルート要素が必要（余分なタグを増やしたくない場合は Fragment <>...</> を使用）。
  • 属性はキャメルケースで書く：onclick → onClick、class → className（class は JS の予約語のため）。

Vì JSX chỉ là JS, bạn dùng thẳng các cấu trúc JS quen thuộc để hiển thị có điều kiện: toán tử ba ngôi ? :, toán tử &&, hoặc if thông thường trước lệnh return.

Rendering Lists & Keyリストのレンダリングと Key

Dùng .map() (giống JS thuần) để biến 1 mảng dữ liệu thành 1 mảng JSX element. Mỗi phần tử trong danh sách bắt buộc có prop đặc biệt key — 1 chuỗi/số định danh duy nhất và ổn định — giúp React nhận biết phần tử nào thay đổi/thêm/xóa giữa các lần render mà không phải render lại toàn bộ danh sách.

（素の JS と同様に）.map() を使ってデータの配列を JSX 要素の配列に変換します。リストの各要素には必ず特別な key prop — 一意で安定した文字列/数値の識別子 — が必要です。これにより React はレンダリング間でどの要素が変更・追加・削除されたかを認識でき、リスト全体を再描画せずに済みます。

const tasks = [
  { id: 1, title: "Learn React" },
  { id: 2, title: "Build a project" },
];

function TaskList() {
  return (
    <ul>
      {tasks.map(task => (
        <li key={task.id}>{task.title}</li>
      ))}
    </ul>
  );
}
Cẩn thận: Đừng dùng index của mảng làm key nếu danh sách có thể thêm/xóa/sắp xếp lại — sẽ khiến React nhận diện sai phần tử, gây bug UI khó phát hiện (đặc biệt khi list chứa input hoặc state riêng từng item).
注意：リストが追加・削除・並べ替えされる可能性がある場合、配列の index を key に使わないでください — React が要素を誤認識し、気づきにくい UI バグの原因になります（特にリスト内に input や各アイテム固有の state がある場合）。

useState — State cơ bảnuseState — 基本的な State

useState là Hook giúp component "ghi nhớ" dữ liệu giữa các lần render và tự động render lại khi dữ liệu đó thay đổi. Khác biệt cốt lõi với biến JS thường: sửa biến thường không làm UI cập nhật, còn gọi hàm setState sẽ báo cho React "vẽ lại" component.

useState はコンポーネントがレンダリング間でデータを「記憶」し、そのデータが変わったときに自動的に再レンダリングされるようにする Hook です。通常の JS 変数との核心的な違い：普通の変数を書き換えても UI は更新されませんが、setState 関数を呼ぶと React に「再描画」を指示できます。

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0); // 0 là giá trị khởi tạo

  return (
    <button onClick={() => setCount(count + 1)}>
      Đã bấm {count} lần
    </button>
  );
}
CODE CŨNhận diện code cũ: Trước khi có Hooks (trước React 16.8), state chỉ tồn tại được trong Class Component qua this.state và this.setState(). Nếu bạn gặp code kiểu dưới đây trong dự án cũ, nó tương đương chính xác ví dụ useState ở trên: 
class Counter extends React.Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };
  }
  render() {
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        Đã bấm {this.state.count} lần
      </button>
    );
  }
}
Code mới hoàn toàn nên viết theo function component + Hooks như ví dụ phía trên — class component vẫn chạy được nhưng không còn được khuyến nghị cho code mới.
旧コード古いコードの見分け方：Hooks 登場前（React 16.8 以前）は、state はクラスコンポーネントの this.state と this.setState() を通じてのみ存在できました。既存プロジェクトで下記のようなコードを見かけたら、それは上の useState の例と全く同じ意味です。新規コードは上記のような関数コンポーネント + Hooks で書くべきで、クラスコンポーネントは動作はしますが新規コードには推奨されません。

React render & commit hoạt động thế nàoReact のレンダーとコミットの仕組み

Mỗi lần cập nhật UI trải qua 3 bước: 1. Trigger (state thay đổi qua setState, hoặc lần render đầu tiên) → 2. Render (React gọi lại hàm component để tính ra JSX mới — chỉ tính toán trong bộ nhớ, chưa đụng vào DOM thật) → 3. Commit (React so sánh (diffing) với lần render trước và chỉ cập nhật đúng những phần DOM thật sự thay đổi).

UI の更新は3ステップを経ます：1. トリガー（setState による state 変更、または初回レンダー）→ 2. レンダー（React がコンポーネント関数を再度呼び出して新しい JSX を計算 — メモリ上での計算のみで、まだ実際の DOM には触れません）→ 3. コミット（React が前回のレンダーと比較（diffing）し、実際に変わった部分の DOM だけを更新）。

Cập nhật state đúng cách: Immutability正しい state 更新：イミュータビリティ

React phát hiện thay đổi bằng cách so sánh tham chiếu (reference), không so sánh nội dung sâu bên trong. Vì vậy, tuyệt đối không sửa trực tiếp object/array trong state (vd: state.push(...) hay state.x = 5) — phải luôn tạo ra object/array mới bằng spread operator ..., nếu không React sẽ không nhận ra là có thay đổi và không render lại.

React は参照（reference）を比較して変更を検出し、内部の値を深く比較するわけではありません。そのため、state の中の object/array を直接変更してはいけません（例：state.push(...) や state.x = 5）— スプレッド構文 ... で常に新しい object/array を作成する必要があります。そうしないと React は変更を検知できず、再レンダリングされません。

// SAI — sửa trực tiếp, React không nhận ra thay đổi
function addTask(task) {
  tasks.push(task);
  setTasks(tasks); // cùng 1 reference -> React bỏ qua
}

// ĐÚNG — tạo mảng mới
function addTask(task) {
  setTasks([...tasks, task]); // reference mới -> React render lại
}

// Object cũng tương tự
setUser({ ...user, name: "Kris mới" });

Lifting State UpState のリフトアップ

Khi 2 component con cần chia sẻ chung 1 state (vd: đồng bộ với nhau), giải pháp chuẩn của React là "nâng" state đó lên component cha gần nhất chứa cả hai, rồi truyền xuống qua props — không phải cố đồng bộ state riêng lẻ giữa 2 component ngang hàng.

2つの子コンポーネントが同じ state を共有する必要がある場合（例：互いに同期させたい）、React の標準的な解決策は、その state を両方を含む最も近い親コンポーネントに「持ち上げ」、props として渡すことです — 兄弟コンポーネント同士で個別の state を無理に同期させるのではありません。

function Parent() {
  const [temperature, setTemperature] = useState(20); // state sống ở đây

  return (
    <>
      <TemperatureInput value={temperature} onChange={setTemperature} />
      <TemperatureDisplay value={temperature} />
    </>
  );
}

function TemperatureInput({ value, onChange }) {
  return <input value={value} onChange={e => onChange(e.target.value)} />;
}

function TemperatureDisplay({ value }) {
  return <p>Nhiệt độ hiện tại: {value}°C</p>;
}

TemperatureInput và TemperatureDisplay là 2 component ngang hàng (sibling), không "biết" tới nhau — cả hai chỉ nhận props từ Parent. Khi input thay đổi, nó gọi onChange để nhờ Parent cập nhật state, Parent re-render và truyền giá trị mới xuống cả 2 con.

TemperatureInput と TemperatureDisplay は互いを「知らない」兄弟コンポーネントです — どちらも Parent から props を受け取るだけです。input が変更されると onChange を呼んで Parent に state の更新を依頼し、Parent が再レンダリングされて新しい値を両方の子に渡します。

useReduceruseReducer

Khi logic cập nhật state phức tạp (nhiều hành động khác nhau cùng tác động lên 1 state), useReducer gom toàn bộ logic đó vào 1 hàm reducer duy nhất — dễ test và dễ theo dõi hơn nhiều lần gọi setState rải rác.

state の更新ロジックが複雑な場合（複数の異なるアクションが1つの state に影響する場合）、useReducer はそのロジックすべてを1つのreducer 関数にまとめます — 散らばった setState の呼び出しより、テストや追跡がずっと簡単になります。

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    default: throw new Error('Unknown action');
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <>
      <button onClick={() => dispatch({ type: 'decrement' })}>-</button>
      {state.count}
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
    </>
  );
}

Context APIContext API

Truyền props qua nhiều tầng component trung gian không cần dùng đến ("prop drilling") là vấn đề phổ biến. Context cho phép 1 component cha "phát sóng" dữ liệu xuống bất kỳ component con nào ở tầng sâu bất kỳ, không cần truyền tay qua từng tầng.

途中のコンポーネントが使わないのに props を何層も渡す（「プロップドリリング」）のはよくある問題です。Context は、親コンポーネントがどれだけ深い階層の子コンポーネントにもデータを「放送」できるようにし、各階層で手動で渡す必要をなくします。

const ThemeContext = createContext('light');

function App() {

function Toolbar() {

Escape Hatches

Escape Hatches

"Escape hatches" là những công cụ để "thoát" khỏi luồng khai báo thuần túy của React khi cần tương tác với thứ nằm ngoài React (DOM API, timer, network...).

「Escape hatches」は、React 外の存在（DOM API、タイマー、ネットワークなど）とやり取りする必要があるときに、React の純粋な宣言的フローから「抜け出す」ためのツールです。

useRefuseRef

useRef tạo ra 1 "hộp chứa" giá trị (.current) có thể thay đổi được mà không kích hoạt render lại — khác hẳn useState. Dùng phổ biến nhất để lấy tham chiếu trực tiếp tới 1 DOM element (vd: tự focus vào input).

useRef は、再レンダリングを引き起こさずに変更できる値の「箱」（.current）を作ります — useState とは大きく異なります。最もよく使われるのは、DOM 要素への直接参照を取得すること（例：input に自動フォーカスする）です。

function SearchInput() {
  const inputRef = useRef(null);

  function handleFocus() {
    inputRef.current.focus(); // thao tác DOM trực tiếp, "thoát" khỏi React
  }

  return (
    <>
      <input ref={inputRef} />
      <button onClick={handleFocus}>Focus vào ô input</button>
    </>
  );
}

useEffect & khi nào KHÔNG cần dùng nóuseEffect と、それが不要な場合

useEffect dùng để đồng bộ hóa component với một hệ thống bên ngoài React (gọi API, đăng ký sự kiện DOM, kết nối WebSocket...), chạy sau khi component đã render lên màn hình. Mảng phụ thuộc (dependency array) tham số thứ 2 quyết định effect chạy lại khi nào; hàm trả về (nếu có) là cleanup function, chạy trước khi effect chạy lại hoặc khi component bị gỡ bỏ.

useEffect は、コンポーネントを React 外部のシステム（API 呼び出し、DOM イベント登録、WebSocket 接続など）と同期させるために使い、コンポーネントが画面にレンダリングされた後に実行されます。第2引数の依存配列（dependency array）は effect がいつ再実行されるかを決め、戻り値の関数（あれば）はクリーンアップ関数で、effect の再実行前やコンポーネントの削除時に実行されます。

useEffect(() => {
  const timer = setInterval(() => console.log("tick"), 1000);
  return () => clearInterval(timer); // cleanup — chạy khi unmount hoặc trước lần effect kế tiếp
}, []); // mảng rỗng = chỉ chạy 1 lần sau lần render đầu tiên
Theo react.dev — "You Might Not Need an Effect": lỗi phổ biến nhất của người mới là dùng useEffect cho những việc không cần effect. Nếu bạn có thể tính toán trực tiếp ngay trong lúc render (vd: giá trị lọc/derived từ props/state có sẵn) thì không cần effect — tính thẳng trong thân hàm component. Effect chỉ nên dùng khi thực sự cần đồng bộ với hệ thống bên ngoài.
react.dev「You Might Not Need an Effect」より：初心者が最もよく犯すミスは、effect が不要な場面で useEffect を使ってしまうことです。レンダー中に直接計算できるもの（例：props/state から導出できるフィルタ済みの値）であれば effect は不要で、コンポーネント関数の中で直接計算すれば十分です。Effect は本当に外部システムとの同期が必要なときにのみ使うべきです。
HAY GẶPVì sao effect của tôi chạy 2 lần? Nếu dùng Vite/Create React App ở chế độ dev, bạn sẽ thấy useEffect chạy 2 lần liên tiếp (mount → cleanup → mount lại) dù code không có gì sai. Đây là hành vi cố ý của <StrictMode> — React chủ động mount/unmount/mount lại trong dev để giúp bạn phát hiện sớm effect thiếu cleanup. Hiện tượng này chỉ xảy ra ở dev, không xảy ra ở bản production. Đừng cố "tắt" nó — thay vào đó hãy đảm bảo effect luôn có cleanup function dọn dẹp đúng những gì nó tạo ra.
よくある疑問なぜ effect が2回実行される？ Vite/Create React App の開発モードでは、コードに問題がなくても useEffect が連続で2回実行される（mount → cleanup → 再mount）ことがあります。これは <StrictMode> の意図的な動作で、React が開発中にわざと mount/unmount/再mount を行い、cleanup が抜けている effect を早期発見できるようにしています。この現象は開発時のみ発生し、本番ビルドでは起こりません。無理に「無効化」しようとせず、effect が作ったものを正しく片付ける cleanup 関数を必ず用意しましょう。

Custom Hooks — tái sử dụng logicカスタムフック — ロジックの再利用

Khi nhiều component lặp lại cùng 1 đoạn logic dùng Hook (vd: theo dõi trạng thái mạng, đếm thời gian...), có thể trích xuất ra thành 1 Custom Hook — 1 hàm JS thường, tên bắt đầu bằng use, được phép gọi các Hook khác bên trong.

複数のコンポーネントが Hook を使った同じロジック（例：ネットワーク状態の監視、タイマーなど）を繰り返している場合、それをカスタムフックとして抽出できます — use で始まる名前の普通の JS 関数で、内部で他の Hook を呼び出せます。

function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine);
  useEffect(() => {
    function update() { setIsOnline(navigator.onLine); }
    window.addEventListener('online', update);
    window.addEventListener('offline', update);
    return () => {
      window.removeEventListener('online', update);
      window.removeEventListener('offline', update);
    };
  }, []);
  return isOnline;
}

// Dùng lại ở bất kỳ component nào:
function StatusBar() {
  const isOnline = useOnlineStatus();
  return <p>{isOnline ? "✅ Online" : "❌ Offline"}</p>;
}

Tối ưu hiệu năng

パフォーマンス最適化

Mặc định, khi component cha render lại, toàn bộ component con cũng render lại theo — kể cả khi props của con không đổi. Với hầu hết ứng dụng, việc này đủ nhanh và không cần lo. Chỉ khi đo đạc thực tế thấy chậm, mới cân nhắc các công cụ dưới đây.

デフォルトでは、親コンポーネントが再レンダリングされると、子コンポーネントもすべて再レンダリングされます — 子の props が変わっていなくてもです。ほとんどのアプリではこれで十分速く、心配は不要です。実際に計測して遅いと分かった場合にのみ、以下のツールを検討しましょう。

  • React.memo: bọc quanh 1 component, giúp nó bỏ qua render lại nếu props truyền vào không đổi.
  • useMemo: ghi nhớ (cache) kết quả của 1 phép tính tốn kém, chỉ tính lại khi dependency thay đổi.
  • useCallback: ghi nhớ 1 hàm, tránh tạo ra hàm mới ở mỗi lần render — hữu ích khi hàm đó được truyền làm prop cho component con đã bọc React.memo.
  • React.memo：コンポーネントをラップし、渡された props が変わらなければ再レンダリングをスキップさせます。
  • useMemo：コストの高い計算結果を記憶（キャッシュ）し、依存関係が変わったときだけ再計算します。
  • useCallback：関数を記憶し、レンダーのたびに新しい関数が作られるのを防ぎます — その関数が React.memo でラップされた子コンポーネントに props として渡される場合に有用です。
const ExpensiveList = React.memo(function ExpensiveList({ items }) {
  console.log("Re-rendering list...");
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
});

function Parent({ items }) {
  const sortedItems = useMemo(
    () => [...items].sort((a, b) => a.name.localeCompare(b.name)),
    [items]
  );
  const handleClick = useCallback(() => console.log("clicked"), []);

  return <ExpensiveList items={sortedItems} onClick={handleClick} />;
}
Lời khuyên từ react.dev: đừng tối ưu sớm. useMemo/useCallback có chi phí riêng (tốn bộ nhớ để ghi nhớ) — chỉ nên dùng sau khi đã xác định rõ đây là điểm nghẽn hiệu năng thật sự, ví dụ bằng React DevTools Profiler.
react.dev のアドバイス：早すぎる最適化は避けましょう。useMemo/useCallback にもコスト（記憶のためのメモリ）がかかります — React DevTools Profiler などで実際のパフォーマンスのボトルネックだと確認できてから使うべきです。

  { path: "/", element: <Home /> },

function App() {

Data Fetchingデータフェッチング

Cách cổ điển là gọi fetch trong useEffect, nhưng cách này tự viết lại nhiều thứ (loading, error, cache, race condition). Thực tế hiện nay các dự án thường dùng thư viện chuyên biệt như TanStack Query hoặc SWR để xử lý cache, refetch, đồng bộ dữ liệu server tốt hơn.

昔ながらの方法は useEffect 内で fetch を呼ぶことですが、これだと loading・error・キャッシュ・競合状態などを自前で書く必要があります。現在の実務では、キャッシュ・再取得・サーバーデータの同期をより良く扱うために TanStack Query や SWR のような専用ライブラリがよく使われます。

// Cách cổ điển trong useEffect
useEffect(() => {
  let ignore = false;
  fetch(`/api/tasks/${id}`)
    .then(res => res.json())
    .then(data => { if (!ignore) setTask(data); });
  return () => { ignore = true; }; // tránh set state sau khi component đã unmount
}, [id]);

Next.js (phát triển bởi Vercel) là framework React phổ biến nhất hiện nay. App Router (từ Next.js 13+) dùng routing theo cấu trúc thư mục — không cần khai báo route thủ công như React Router: mỗi thư mục trong app/ chứa file page.tsx tương ứng với 1 URL.

Next.js（Vercel 開発）は現在最も広く使われている React フレームワークです。App Router（Next.js 13 以降）はディレクトリ構造によるルーティングを採用しており、React Router のように手動でルートを宣言する必要はありません：app/ 内の各ディレクトリが page.tsx ファイルを持ち、それぞれが1つの URL に対応します。

app/
├── layout.tsx        → layout dùng chung cho mọi trang
├── page.tsx          → route "/"
├── about/
│   └── page.tsx      → route "/about"
└── blog/
    └── [slug]/
        └── page.tsx  → route động "/blog/:slug"

Điểm khác biệt lớn nhất so với React thông thường: trong App Router, mọi component mặc định là Server Component — chạy trên server, không gửi JS xuống trình duyệt, và có thể async để fetch dữ liệu trực tiếp mà không cần useEffect.

通常の React との最大の違いは、App Router ではすべてのコンポーネントがデフォルトで Server Component である点です — サーバー上で実行され、ブラウザに JS を送信せず、async にしてデータを直接フェッチでき、useEffect は不要です。

// app/page.tsx — Server Component (mặc định, KHÔNG cần "use client")
export default async function HomePage() {
  const tasks = await fetch('https://api.example.com/tasks').then(r => r.json());
  return (
    <main>
      <h1>Danh sách Task</h1>
      <TaskList tasks={tasks} />
    </main>
  );
}

Khi component cần useState, useEffect, hoặc event handler (những thứ chỉ chạy được ở trình duyệt), phải khai báo 'use client' ở dòng đầu file — biến nó thành Client Component, giống React bình thường bạn đã học ở các mục trước.

コンポーネントが useState、useEffect、イベントハンドラ（ブラウザでしか動かないもの）を必要とする場合は、ファイルの先頭に 'use client' を宣言する必要があります — これにより、これまでの章で学んだ通常の React と同じClient Component になります。

// app/components/LikeButton.tsx — Client Component
'use client';
import { useState } from 'react';

export default function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? '❤️ Đã thích' : '🤍 Thích'}
    </button>
  );
}

// app/blog/[slug]/page.tsx
export default async function BlogPost({ params }) {

Framework khác: Astro & Expoその他のフレームワーク：Astro と Expo

Astro nhắm tới các trang nặng nội dung (blog, trang giới thiệu, tài liệu): mặc định Astro render ra HTML/CSS tĩnh, không gửi 1 dòng JS nào xuống trình duyệt — tải cực nhanh. Khi cần 1 phần tương tác (vd: nút đếm lượt thích), bạn nhúng nguyên 1 component React vào làm "đảo tương tác" (island) bằng directive client:load, phần còn lại của trang vẫn tĩnh hoàn toàn.

Astro はコンテンツ量の多いサイト（ブログ、紹介ページ、ドキュメント）向けです：デフォルトで Astro は静的な HTML/CSS を出力し、ブラウザにJS を一切送信しません — 読み込みが非常に高速です。インタラクティブな部分（例：いいねボタン）が必要な場合は、client:load ディレクティブで React コンポーネントをまるごと「インタラクティブな島」（island）として埋め込め、ページの残り部分は完全に静的なままです。

---
// src/pages/index.astro
import LikeButton from '../components/LikeButton.jsx';
---
<html>
  <body>
    <h1>Bài viết blog (hoàn toàn tĩnh, 0 JS)</h1>
    <p>Nội dung bài viết...</p>
    <LikeButton client:load />  {/* chỉ phần này có JS/React */}
  </body>
</html>

Expo là framework để xây ứng dụng di động (React Native) bằng đúng kiến thức React đã học — component, props, state, hooks giống hệt, chỉ khác thẻ JSX (<View>, <Text> thay vì <div>, <p>) vì render ra native UI thay vì DOM. expo-router dùng routing theo cấu trúc thư mục giống hệt Next.js App Router.

Expo は、学んだ React の知識（コンポーネント、props、state、hooks は全く同じ）でモバイルアプリ（React Native）を構築するためのフレームワークです。異なるのは JSX タグだけです（DOM ではなくネイティブ UI をレンダリングするため <div>、<p> の代わりに <View>、<Text> を使用）。expo-router は Next.js の App Router と全く同じディレクトリ構造ベースのルーティングを使います。

npx create-expo-app my-app
cd my-app
npx expo start   # quét QR code bằng app Expo Go để xem trực tiếp trên điện thoại
Chọn framework nào? Web app cần SEO/hiệu năng tải trang (ecommerce, dashboard công khai) → Next.js. Blog/trang giới thiệu/tài liệu → Astro. Ứng dụng di động → Expo. App nội bộ đơn giản, không cần SEO, ít route → Vite thuần vẫn hoàn toàn ổn, không bắt buộc phải dùng framework.
どのフレームワークを選ぶ？ SEO やページ読み込み速度が重要な Web アプリ（EC サイト、公開ダッシュボード）→ Next.js。ブログ・紹介ページ・ドキュメント → Astro。モバイルアプリ → Expo。SEO が不要でルートも少ないシンプルな社内アプリ → Vite だけで十分で、フレームワークは必須ではありません。

AWS Global Infrastructure: Region, AZ, Edge Location
Tóm tắt

Region = 1 khu vực địa lý độc lập (vd ap-southeast-1), chọn Region gần user để giảm latency và đáp ứng yêu cầu chủ quyền dữ liệu (data residency). Availability Zone (AZ) = 1 hoặc nhiều datacenter vật lý tách biệt trong 1 Region, các AZ cách nhau đủ xa để không cùng bị ảnh hưởng bởi 1 sự cố nhưng đủ gần để latency thấp giữa các AZ. Edge Location/Point of Presence = điểm cache gần người dùng cuối, dùng bởi CloudFront/Global Accelerator/Route 53.

Điểm quan trọng
  • Mỗi Region có tối thiểu 3 AZ (một số Region có nhiều hơn), mỗi AZ cách nhau vài km, kết nối bằng cáp quang tốc độ cao, độ trễ thấp.
  • Tài nguyên như VPC là region-scoped; subnet, EC2, EBS là AZ-scoped; IAM, Route 53, S3 (namespace) là global.
  • Số lượng Edge Location (400+) nhiều hơn hẳn số Region (30+) — vì mục tiêu là "gần người dùng nhất có thể".
  • Chọn Region còn ảnh hưởng tới giá dịch vụ (khác nhau giữa các Region) và độ trễ pháp lý/compliance (dữ liệu công dân EU nên ở Region EU).

IAM Users, Groups & Policies
Tóm tắt

Khi tạo tài khoản AWS, mặc định chỉ có 1 identity duy nhất là root user — có toàn quyền, không nên dùng cho công việc hàng ngày. IAM User đại diện cho 1 người/ứng dụng cụ thể trong tổ chức. Amazon EC2 — Instance Storage

EBS vs Instance Store
Tóm tắt

EBS (Elastic Block Store): ổ đĩa mạng, tồn tại độc lập với instance (có thể detach/reattach), hỗ trợ snapshot, giới hạn theo AZ. Instance Store: ổ đĩa vật lý gắn liền phần cứng host, hiệu năng IOPS cực cao nhưng ephemeral — mất sạch dữ liệu khi instance dừng/terminate.

Điểm quan trọng
  • EBS volume chỉ gắn được cho instance trong cùng AZ; muốn dùng ở AZ khác phải tạo snapshot rồi restore volume mới.
  • gp3: SSD đa dụng, 3,000 IOPS baseline (tăng riêng không cần tăng dung lượng); io2 Block Express: tới 256,000 IOPS, dùng cho DB tải cao.
  • Instance Store cho throughput/IOPS cao hơn hẳn EBS vì không qua network — nhưng dữ liệu mất khi Stop/Terminate (Reboot thì vẫn giữ).
  • EBS hỗ trợ Multi-Attach (chỉ io1/io2) — gắn 1 volume cho nhiều instance cùng lúc trong cùng AZ.
Use case

Cần dữ liệu bền vững qua các lần restart → EBS. Cần cache tạm thời/buffer với IOPS cực cao, chấp nhận mất khi restart → Instance Store.

High Availability & Scalability

2 khái niệm hay bị nhầm lẫn: Scalability = hệ thống chịu tải tăng bằng cách thêm tài nguyên (scale out/up); High Availability = hệ thống vẫn chạy được khi 1 phần gặp sự cố, thường đạt được bằng cách chạy dư thừa (redundancy) qua ≥2 AZ.

Elastic Load Balancing (ELB): ALB vs NLB vs GWLB
Tóm tắt

Load Balancer là 1 server đứng trước nhiều EC2/target, phân phối traffic đều ra, đồng thời là "single point of contact" duy nhất mà client cần biết (client không cần biết có bao nhiêu server phía sau).

Load Balancer phân phối traffic đều tới EC2 instance trải trên nhiều AZ
Điểm quan trọng
  • ALB (Application LB, Layer 7): hiểu nội dung HTTP/HTTPS → routing theo path (/api vs /images), host, header, query string; hỗ trợ WebSocket, tích hợp trực tiếp target là Lambda function.
  • NLB (Network LB, Layer 4): chỉ xử lý TCP/UDP, không hiểu nội dung — đổi lại hiệu năng cực cao (hàng triệu request/giây), độ trễ thấp nhất, hỗ trợ gán Elastic/static IP cố định cho mỗi AZ.
  • GWLB (Gateway LB, Layer 3): dùng để chèn 1 thiết bị bảo mật ảo bên thứ 3 (firewall, IDS/IPS) vào giữa luồng traffic mà ứng dụng không hề hay biết ("transparent").
  • Cả 3 loại đều có thể cấu hình health check để tự động ngừng gửi traffic tới target đang lỗi.
Use case

App web cần route /api và /images tới 2 target group khác nhau → ALB. Game server/IoT cần xử lý hàng triệu request/giây, độ trễ cực thấp → NLB.

Tóm tắt

Điểm quan trọng

  • Scheduled Scaling: đổi capacity theo lịch biết trước (vd tăng sẵn trước 8h sáng mỗi ngày).
  • ASG luôn cố gắng phân bổ instance đều qua nhiều AZ đã cấu hình để tối đa hóa tính sẵn sàng.
  • Cooldown period: sau mỗi lần scale, ASG chờ 1 khoảng thời gian trước khi scale tiếp, tránh phản ứng thái quá với biến động ngắn hạn.

RDS Multi-AZ vs Read Replica vs RDS Proxy
Tóm tắt

2 khái niệm dễ gây nhầm lẫn nhất trong bài thi vì tên gọi "giống nhau" nhưng mục đích hoàn toàn khác biệt: Multi-AZ phục vụ Disaster Recovery, còn Read Replica phục vụ Performance/Scaling.

Multi-AZ: bản sao chờ sẵn để failover, không nhận query. Read Replica: nhận query đọc để giảm tải cho Primary
Điểm quan trọng
  • Multi-AZ: replicate đồng bộ (synchronous) sang standby ở AZ khác cùng Region · standby không nhận query · khi Primary lỗi, RDS tự động failover sang standby (đổi DNS endpoint, ứng dụng không cần đổi connection string) · bật/tắt bất kỳ lúc nào chỉ với 1 cú click, không cần thay đổi code.
  • Read Replica: replicate bất đồng bộ (asynchronous), có thể đặt ở AZ khác hoặc Region khác · nhận được SELECT query để giảm tải đọc cho Primary · tối đa 15 read replica cho 1 Primary · có thể tự nâng cấp (promote) 1 Read Replica thành DB độc lập nếu cần.
  • RDS Proxy: nằm giữa ứng dụng và RDS, duy trì pool connection có sẵn (connection pooling) — giải quyết vấn đề Lambda mở quá nhiều connection ngắn hạn làm cạn kiệt RDS; cũng giúp failover nhanh hơn (tới 66%) vì Proxy tự động route sang instance mới.
Use case

Ứng dụng đọc nhiều gấp 10 lần ghi (vd trang tin tức) → thêm Read Replica để san tải đọc. Cần đảm bảo DB không downtime khi AZ gặp sự cố → bật Multi-AZ. Lambda gọi RDS liên tục gây hết connection → RDS Proxy.

Tóm tắt

Classic Solutions Architecture

Các pattern kiến trúc kinh điển thường lặp lại trong đề thi — kết hợp nhiều service đã học ở trên.

3-Tier Web Architecture
Tóm tắt

Kiến trúc web kinh điển chia thành 3 tầng độc lập, mỗi tầng scale riêng: Presentation (CloudFront + S3/ALB — nhận request từ người dùng), Application (ASG + EC2/ECS trong private subnet — xử lý logic nghiệp vụ), Data (RDS Multi-AZ/DynamoDB — lưu trữ dữ liệu bền vững).

Điểm quan trọng
  • Tầng Application luôn đặt ở private subnet, chỉ nhận traffic từ Load Balancer ở tầng Presentation — không public trực tiếp.
  • Mỗi tầng scale độc lập: tăng EC2 ở Application không ảnh hưởng tầng Data, và ngược lại.
  • Stateless ở tầng Application: không lưu session cục bộ trên EC2 (dùng ElastiCache/DynamoDB làm session store) — giúp Auto Scaling thêm/bớt instance bất kỳ lúc nào mà không mất session người dùng.
  • Golden AMI: đóng gói sẵn AMI có cài đặt hoàn chỉnh để ASG launch instance mới nhanh, không cấu hình thủ công mỗi lần scale.

Amazon SQS — Queue là gì?
Tóm tắt

Một queue (hàng đợi) đứng giữa Producer (bên gửi message) và Consumer (bên xử lý message), giúp 2 bên không cần biết tới nhau và không cần chạy cùng tốc độ — Producer cứ gửi (Send), Consumer tự lấy về xử lý (Poll) theo khả năng của mình. Đây chính là ý nghĩa của "decouple" (tách rời).

Nhiều Producer gửi message vào 1 SQS Queue; nhiều Consumer tự poll message về xử lý
Điểm quan trọng
  • Consumer tự kéo (poll) message về — SQS không tự đẩy message tới consumer (khác với SNS).
  • Sau khi 1 consumer lấy message, message bị "ẩn" khỏi queue trong khoảng Visibility Timeout (mặc định 30s) — nếu consumer xử lý xong và gọi DeleteMessage trước khi hết timeout thì message bị xóa hẳn; nếu không, message hiện lại cho consumer khác lấy (chống mất message khi consumer chết giữa chừng).
  • Nhiều consumer có thể cùng đọc 1 queue để tăng throughput xử lý — đây là cách SQS hỗ trợ scale chiều consumer.
Amazon SQS — Standard Queue vs FIFO Queue
Tóm tắt

Standard Queue là loại queue mặc định, tồn tại hơn 10 năm, tối ưu cho throughput cao. FIFO Queue (tên đuôi bắt buộc .fifo) đánh đổi throughput lấy tính đúng thứ tự và không trùng lặp.

Điểm quan trọng
  • Standard: throughput gần như không giới hạn · độ trễ thấp (<10ms) · giới hạn 256KB/message · retention mặc định 4 ngày (tối đa 14 ngày) · at-least-once delivery (đôi khi trùng message) · best-effort ordering (không đảm bảo đúng thứ tự tuyệt đối).
  • FIFO: đảm bảo thứ tự (First-In-First-Out) trong cùng 1 Message Group ID · exactly-once processing (không trùng lặp, nhờ cơ chế loại trùng trong 5 phút) · throughput giới hạn 300 msg/s (hoặc 3,000 msg/s nếu bật batching).
  • Message lớn hơn 256KB → dùng SQS Extended Client Library, lưu payload thật trong S3, chỉ gửi con trỏ (pointer) qua SQS.
  • Dead Letter Queue (DLQ): sau N lần xử lý thất bại, message tự động chuyển sang 1 queue riêng để debug thay vì bị xử lý lặp vô hạn.
Use case

Xử lý hàng triệu log event, không quan trọng thứ tự tuyệt đối → Standard Queue. Xử lý lệnh giao dịch ngân hàng phải đúng tuần tự, không được xử lý trùng → FIFO Queue.

Điểm quan trọng

Tóm tắt

Use case

Disaster Recovery & Migrations

DR Strategies: Backup & Restore / Pilot Light / Warm Standby / Multi-site Active-Active
Tóm tắt

4 chiến lược DR theo chi phí tăng dần & RTO/RPO giảm dần: Backup & Restore (rẻ nhất, RTO/RPO cao) → Pilot Light (hạ tầng lõi luôn chạy tối thiểu) → Warm Standby (bản scale-down chạy sẵn) → Multi-site Active-Active (chạy song song đầy đủ, RTO/RPO gần 0, đắt nhất).

Điểm quan trọng
  • RTO (Recovery Time Objective): thời gian tối đa chấp nhận được để khôi phục hệ thống sau sự cố. RPO (Recovery Point Objective): lượng dữ liệu tối đa chấp nhận mất (tính theo thời gian kể từ backup gần nhất).
  • Backup & Restore: chỉ lưu snapshot/backup định kỳ, RTO/RPO tính bằng giờ.
  • Pilot Light: DB luôn sync sẵn, phần compute (EC2) tắt sẵn, chỉ bật lên khi cần — RTO tính bằng chục phút.
  • Warm Standby: toàn bộ hệ thống chạy sẵn ở quy mô nhỏ (scaled-down), chỉ cần scale up khi failover — RTO tính bằng phút.
  • Multi-site Active-Active: cả 2 Region cùng phục vụ traffic thật, RTO/RPO gần 0 nhưng tốn gấp đôi chi phí vận hành.
Chi phí tăng dần, RTO/RPO giảm dần từ trái sang phải
Use case

Ngân sách hạn chế, chấp nhận downtime vài giờ → Backup & Restore. Không chấp nhận downtime → Active-Active.

Introduction to Artificial Intelligence (AI)

AI vs ML vs Deep Learning
Tóm tắt

AI = khái niệm rộng nhất, máy móc mô phỏng hành vi/trí thông minh con người. ML (Machine Learning) = tập con của AI, máy "học" từ dữ liệu thay vì lập trình luật cứng (rule-based). Deep Learning = tập con của ML, dùng mạng neural network nhiều lớp (layer), mạnh với dữ liệu phi cấu trúc (ảnh, âm thanh, văn bản) nhưng cần nhiều dữ liệu & compute hơn.

Điểm quan trọng
  • 3 khái niệm là quan hệ lồng nhau (nested): mọi Deep Learning đều là ML, mọi ML đều là AI — nhưng chiều ngược lại không đúng.
  • ML truyền thống cần con người tự chọn feature quan trọng; Deep Learning tự học feature từ dữ liệu thô, ít cần can thiệp thủ công hơn.
  • Generative AI (học ở mục sau) là 1 nhánh ứng dụng của Deep Learning, chuyên về việc tạo ra nội dung mới thay vì chỉ dự đoán/phân loại.
Deep Learning ⊂ Machine Learning ⊂ Artificial Intelligence
Use case

Bài toán đơn giản, dữ liệu dạng bảng (tabular) → ML truyền thống (regression, decision tree). Nhận diện ảnh/giọng nói phức tạp → Deep Learning.

Keyword trong đề

subset ofneural networkunstructured datarule-based vs learned

Supervised · Unsupervised · Reinforcement Learning
Tóm tắt

Supervised learning: học từ dữ liệu đã có nhãn (labeled) — vd dự đoán giá nhà, phân loại email spam. Unsupervised learning: học từ dữ liệu không nhãn, tự tìm pattern — vd phân cụm khách hàng (clustering). Reinforcement learning: agent học qua thử-sai, nhận reward/penalty theo hành động — vd robot, game AI.

Điểm quan trọng
  • Supervised chia làm 2 loại bài toán: Classification (dự đoán 1 nhãn/danh mục, vd spam/không spam) và Regression (dự đoán 1 giá trị số liên tục, vd giá nhà).
  • Unsupervised phổ biến nhất là Clustering (nhóm dữ liệu tương tự) và giảm chiều dữ liệu (dimensionality reduction).
  • Reinforcement Learning không cần dữ liệu nhãn sẵn — agent tự khám phá qua tương tác với môi trường, tối ưu theo tổng reward tích lũy dài hạn.
Use case

Có dữ liệu lịch sử với kết quả biết trước (khách hàng đã rời bỏ hay chưa) → Supervised (classification). Không biết trước nhóm nào, muốn máy tự phân nhóm khách hàng → Unsupervised (clustering).

Keyword trong đề

labeled dataunlabeled dataclassification / regression / clusteringreward and penalty

Các loại dữ liệu — labeled/unlabeled, structured (tabular) vs unstructured (text/image/audio), time-series.
Batch vs Real-time inferencing — Batch: xử lý hàng loạt định kỳ, không cần phản hồi ngay (vd báo cáo đêm). Real-time: trả kết quả ngay lập tức (vd chatbot, gợi ý sản phẩm).
Bias, Fairness, Fit — Bias: model thiên lệch do dữ liệu huấn luyện không đại diện. Overfitting: model học "thuộc lòng" dữ liệu train, dự đoán kém trên dữ liệu mới. Underfitting: model quá đơn giản, không học được pattern.

Amazon Bedrock and GenAI

Generative AI & Foundation Models — khái niệm nền
Tóm tắt

Foundation Model: model rất lớn được pre-train trên khối dữ liệu khổng lồ, có thể thích ứng (adapt) cho nhiều tác vụ khác nhau. Token: đơn vị nhỏ nhất model xử lý (thường ~1 từ hoặc mảnh từ). Embedding: biểu diễn dữ liệu (text/ảnh) thành vector số học, dữ liệu có ý nghĩa gần nhau thì vector gần nhau. Transformer: kiến trúc neural network đứng sau hầu hết LLM hiện nay, dùng cơ chế "attention" để hiểu ngữ cảnh.

Điểm quan trọng
  • Model càng nhiều token trong "context window" thì càng "nhớ" được nhiều nội dung hội thoại/tài liệu cùng lúc, nhưng chi phí (token-based pricing) cũng tăng theo.
  • Multi-modal model: xử lý được nhiều loại input/output khác nhau trong 1 model (text + ảnh + audio) thay vì chỉ text.
  • Diffusion model: kiến trúc đứng sau các model sinh ảnh (image generation) — khác cơ chế với transformer sinh text.
  • 2 model có kiến trúc giống nhau nhưng khác dữ liệu train → cho ra hành vi/kiến thức khác hẳn nhau.
Use case

Cần tìm kiếm theo "ý nghĩa" thay vì khớp từ khóa chính xác → dùng embedding + vector search.

Keyword trong đề

Amazon Bedrock
Tóm tắt

Dịch vụ serverless, fully-managed cho phép truy cập nhiều foundation model từ nhiều nhà cung cấp (Anthropic, Meta, Amazon Nova, Mistral...) qua 1 API duy nhất — không cần tự quản lý hạ tầng. Hỗ trợ: Knowledge Bases (RAG có sẵn), Agents (thực hiện tác vụ nhiều bước, gọi API/tool), Guardrails (lọc nội dung không phù hợp), và fine-tuning/continued pre-training.

Điểm quan trọng
  • Bedrock tính phí theo token (on-demand) hoặc Provisioned Throughput (cam kết trước, phù hợp tải cao ổn định).
  • Agents for Bedrock tự chia nhỏ 1 yêu cầu phức tạp thành nhiều bước, tự quyết định khi nào cần gọi API/tool ngoài (vd tra cứu database) trước khi trả lời.
  • Dữ liệu gửi vào Bedrock không được dùng để train lại model nền của nhà cung cấp — quan trọng cho yêu cầu bảo mật/compliance doanh nghiệp.
  • Có thể so sánh nhiều model cùng lúc ngay trong Bedrock Playground trước khi chọn model phù hợp nhất cho use case.
Use case

Muốn thử nhiều LLM khác nhau (Claude, Llama, Nova...) mà không tự host hạ tầng GPU → Bedrock. Cần chatbot trả lời dựa trên tài liệu nội bộ công ty → Bedrock Knowledge Base (RAG).

Retrieval-Augmented Generation (RAG)
Tóm tắt

RAG cho phép LLM trả lời dựa trên dữ liệu ngoài phạm vi đã train (vd tài liệu nội bộ, dữ liệu mới nhất): hệ thống truy xuất (retrieve) đoạn văn bản liên quan từ vector database, rồi đưa vào prompt cùng câu hỏi để model sinh câu trả lời — giúp giảm hallucination, cập nhật kiến thức mà không cần fine-tune lại model.

Điểm quan trọng
  • Quy trình gồm 2 giai đoạn: Ingestion (chia nhỏ tài liệu thành chunk, tạo embedding, lưu vào vector DB — làm trước) và Query time (embedding câu hỏi, tìm chunk gần nhất, đưa vào prompt).
  • RAG rẻ hơn nhiều so với fine-tuning vì không cần train lại trọng số model — chỉ cần cập nhật vector database khi tài liệu thay đổi.
  • Amazon Bedrock Knowledge Bases tự động hóa toàn bộ pipeline này (chunking, embedding, lưu trữ, truy xuất) mà không cần tự code.
  • Chất lượng RAG phụ thuộc nhiều vào cách chunking (chia tài liệu quá to/nhỏ đều giảm độ chính xác truy xuất).
Câu hỏi → tìm chunk liên quan trong vector DB → ghép vào prompt → LLM sinh câu trả lời

Prompt Engineering

Kỹ thuật Prompting: Zero-shot, Few-shot, Chain-of-Thought
Tóm tắt

Zero-shot: hỏi thẳng, không kèm ví dụ. Single/Few-shot: kèm 1 hoặc vài ví dụ mẫu trong prompt để model bắt chước định dạng/phong cách. Chain-of-Thought (CoT): yêu cầu model "suy nghĩ từng bước" trước khi trả lời — cải thiện đáng kể độ chính xác với bài toán logic/tính toán.

Điểm quan trọng
  • Model càng lớn/hiện đại thì zero-shot càng hiệu quả — model nhỏ/cũ thường cần few-shot để đạt chất lượng tốt.
  • Chain-of-Thought chỉ cần thêm cụm từ đơn giản như "hãy suy nghĩ từng bước" vào cuối prompt — không cần kỹ thuật phức tạp.
  • Prompt Template: khuôn mẫu có sẵn với chỗ trống (placeholder) để tái sử dụng cho nhiều input khác nhau, đảm bảo tính nhất quán.
3 kỹ thuật prompting phổ biến nhất trong đề thi
Use case

Cần model trả lời theo đúng 1 định dạng JSON cụ thể → Few-shot (cho vài ví dụ định dạng mong muốn). Bài toán suy luận nhiều bước (toán, logic) → Chain-of-Thought.

Inference Parameters
Tóm tắt

Temperature (0–1): giá trị thấp → câu trả lời ổn định, ít sáng tạo, dễ đoán; giá trị cao → đa dạng/sáng tạo hơn nhưng dễ "lạc đề". Top-P / Top-K: giới hạn tập từ ứng viên model chọn ở mỗi bước sinh chữ. Max tokens (output length): giới hạn độ dài câu trả lời.

Điểm quan trọng
  • Top-K: chỉ chọn trong K từ có xác suất cao nhất; Top-P (nucleus sampling): chọn trong tập từ nhỏ nhất có tổng xác suất ≥ P — cả 2 đều kiểm soát độ "an toàn" của từ được chọn.
  • Temperature = 0 gần như deterministic (luôn ra cùng 1 câu trả lời cho cùng input) — hữu ích khi cần kết quả tái lập được (reproducible).
  • Max tokens cắt ngang câu trả lời nếu đạt giới hạn — cần đặt đủ lớn cho câu trả lời dài (code, bài luận) để tránh bị cắt cụt.
Use case

Cần câu trả lời nhất quán, đúng sự thật (vd trả lời câu hỏi pháp lý) → temperature thấp. Cần viết nội dung sáng tạo (thơ, ý tưởng marketing) → temperature cao.

Keyword trong đề

temperaturemore deterministic vs more creativeoutput length

Rủi ro của Prompt Engineering — Prompt Injection/Hijacking: chèn chỉ thị độc hại vào input để đánh lừa model làm việc ngoài ý muốn. Jailbreaking: cố tình lách guardrail để model trả lời nội dung bị cấm. Exposure: rò rỉ system prompt/dữ liệu nhạy cảm qua câu trả lời. Poisoning: đầu độc dữ liệu huấn luyện/ngữ cảnh để model học sai lệch có chủ đích.
Best practice — viết prompt rõ ràng, cụ thể (specific & concise), tách rõ instruction/context/input bằng định dạng riêng biệt, luôn kết hợp Guardrails khi triển khai production.

AI and Machine Learning (ML)

ML Development Lifecycle
Tóm tắt

Quy trình chuẩn: Thu thập dữ liệu → EDA (phân tích khám phá dữ liệu) → Tiền xử lý & Feature Engineering → Huấn luyện (Training) → Tinh chỉnh hyperparameter → Đánh giá (Evaluation) → Triển khai (Deployment) → Giám sát (Monitoring). Đây là vòng lặp liên tục, không phải quy trình 1 chiều — model cần retrain khi hiệu năng suy giảm (model drift).

Điểm quan trọng
  • EDA: hiểu phân bố, phát hiện giá trị thiếu/bất thường trước khi xử lý — luôn làm trước khi train.
  • Feature Engineering: biến đổi dữ liệu thô thành đặc trưng (feature) hữu ích hơn cho model (vd chuẩn hóa, mã hóa danh mục).
  • Model Monitoring phát hiện model drift (hiệu năng giảm dần do dữ liệu thực tế thay đổi so với lúc train) — dấu hiệu cần retrain.
  • Vòng lặp này lặp lại liên tục trong suốt vòng đời sản phẩm, không kết thúc sau lần deploy đầu tiên.
Vòng lặp liên tục — không dừng lại sau khi deploy lần đầu
Use case

Đề bài mô tả 1 bước cụ thể (vd "làm sạch dữ liệu, xử lý giá trị thiếu") và hỏi đây thuộc giai đoạn nào → đối chiếu với lifecycle trên (ở đây là Data Pre-processing).

Keyword trong đề

data collectionfeature engineeringhyperparameter tuningmodel monitoring / drift

MLOps — áp dụng thực hành DevOps cho ML: tự động hóa pipeline, quy trình lặp lại được (repeatable), quản lý phiên bản model, retrain tự động.
Model performance metrics — Accuracy, AUC (Area Under ROC Curve), F1 score: đo hiệu năng kỹ thuật của model.
Business metrics — ROI, cost per user, customer feedback: đo giá trị kinh doanh thực tế — đề hay yêu cầu phân biệt 2 loại metric này.

Amazon SageMaker

SageMaker — nền tảng xây/train/deploy model tùy chỉnh
Tóm tắt

Khác với các Managed AI Service (dùng ngay, không tùy biến), SageMaker là nền tảng full-lifecycle để tự xây dựng, huấn luyện, và triển khai model ML/AI của riêng bạn khi các managed service có sẵn không đáp ứng đủ nhu cầu đặc thù.

Điểm quan trọng
  • SageMaker hỗ trợ 3 cách deploy model: Real-time endpoint (phản hồi ngay), Batch Transform (xử lý hàng loạt offline), Serverless Inference (tự scale, trả tiền theo request).
  • Có thể mang thuật toán/framework riêng (bring your own container) hoặc dùng thuật toán built-in sẵn có của SageMaker.
  • SageMaker quản lý toàn bộ hạ tầng training (cluster GPU/CPU tạm thời) — tự tắt sau khi train xong, chỉ trả tiền theo thời gian thực sự dùng.
Use case

Cần model dự đoán riêng theo dữ liệu đặc thù ngành mà không dịch vụ có sẵn nào đáp ứng được → SageMaker tự train model custom.

Keyword trong đề

build, train, and deploy custom modelsfull control

SageMaker JumpStart — hub model có sẵn (foundation model + model mã nguồn mở) để triển khai/tinh chỉnh nhanh, không cần train từ đầu.
SageMaker Studio — IDE tích hợp cho toàn bộ vòng đời ML (notebook, pipeline, debugging) trong 1 giao diện.
SageMaker Data Wrangler — chuẩn bị & làm sạch dữ liệu bằng giao diện trực quan, ít code.
SageMaker Feature Store — kho lưu trữ & tái sử dụng feature đã xử lý giữa nhiều model/team.
SageMaker Model Monitor — giám sát model đang chạy production, phát hiện model drift/suy giảm chất lượng.
SageMaker Clarify — phát hiện bias trong dữ liệu/model, giải thích (explainability) quyết định của model.
SageMaker Model Cards — tài liệu hóa thông tin model (mục đích, giới hạn, hiệu năng) phục vụ minh bạch & governance.

Responsible AI, Security, Compliance and Governance

Trụ cột Responsible AI
Tóm tắt

Các đặc điểm của AI có trách nhiệm: Fairness (công bằng, không thiên lệch nhóm nào), Robustness (bền vững trước dữ liệu bất thường), Safety, Veracity (tính xác thực, ít hallucination), Transparency & Explainability (giải thích được vì sao model ra quyết định đó).

Điểm quan trọng
  • Bias thường bắt nguồn từ dữ liệu training không đại diện đầy đủ cho thực tế (vd thiếu mẫu 1 nhóm nhân khẩu học).
  • Overfitting (học thuộc lòng, kém với dữ liệu mới) và Underfitting (quá đơn giản, không học được pattern) đều ảnh hưởng tới độ tin cậy của model.
  • Explainability quan trọng nhất ở các ngành có quy định chặt (tài chính, y tế, tuyển dụng) — nơi cần giải trình được lý do ra quyết định.
Use case

Model tuyển dụng bị nghi ngờ thiên vị giới tính → dùng SageMaker Clarify để phát hiện bias trong dữ liệu/model trước khi triển khai.

Keyword trong đề

bias and fairnessexplainabilitytransparent modelhallucination

Amazon A2I — con người review lại các quyết định AI có độ tin cậy thấp trước khi áp dụng.
